# 门禁修订协议 / Gate Amendment Protocol

> **适用对象**：`architect_gatekeeper.py`（首席架构师验收门禁）。
> **权限**：施工方（现任/前任/任何 AI 代理）只能**提案**并附测试；**启用裁定权属架构师**（用户或其指定人）。
> 本协议自 v1.1 修订起生效（2026-11-12，架构师指令"你接手"授权制定）。

---

## 一、为什么门禁可以改，以及为什么不能随便改

门禁必须能随施工发现演化，否则系统性缺陷永远拦不住；但"被验收方修改验收器"会摧毁信任链。
解法：**修订不是禁止，而是换轨**——门禁修订不走施工方的 RSI 编译轨道，走本协议的
独立治理轨道：提案 → 测试 → 架构师裁定 → 版本化启用。工作流与子代理**永不**触碰门禁文件。

## 二、修订五标准（全部满足才可启用）

| # | 标准 | 含义 | 判定方式 |
| --- | --- | --- | --- |
| S1 | **系统性缺陷门槛** | 只接受机械可检的缺陷类（白名单/正则/计数），且有重复发生实证（≥2 次，或单次扫查出整类） | 提案须附事故编号（LESSONS L 编号/批次号）与出现次数 |
| S2 | **只加严不放松** | 只能新增检查或加严现有检查；删除/放松现有检查一票否决 | diff 审查：任何 `-` 行删除既有 fail 条件即驳回 |
| S3 | **渐进启用（回归门槛）** | 新检查须在当前封存语料上全量 PASS 才可启用；当下过不了的检查只能挂"草案+测试+启用条件" | 启用前必须实跑门禁并附 `[PASS]` 输出 |
| S4 | **版本化留痕** | 版本号 + 文件头 changelog（日期/规则/动机/测试证据）；无版本号改动无效 | 检查 `Version history` 段 |
| S5 | **裁判与修复分离** | 门禁只裁判不修复；修复逻辑留在 `literature/tools/` 与工作流 | 提案中不得含写文件/改数据动作 |

补充：语义裁决类问题（"图上到底写了什么"）**永远不进**门禁——归人工校对线
（[COLLATION_GUIDE.md](COLLATION_GUIDE.md)）。

## 三、修订流程（六步）

1. **提案**：施工方撰写 `docs/gate_amendments/vX.Y_proposal.md`：规则描述、动机事故、
   拟议 diff、回归证据（现行语料 `[PASS]` 输出）、正例/反例测试样本；
2. **测试**：反例（旧门禁放过、新门禁拦住）与正例（合法数据不被误杀）各至少 1 组；
3. **裁定**：架构师批准/驳回/挂账（挂账须写明启用条件）；
4. **实施**：架构师或其指定人修改 `architect_gatekeeper.py`（含版本头 changelog）；
5. **回归**：实跑 `python architect_gatekeeper.py`，须 `[PASS]`；
6. **留痕**：CHANGELOG + 本文件"修订记录"表更新。

## 五、与 RSI 闭环的关系

- 施工方 RSI（[METHODOLOGY.md](METHODOLOGY.md) §6）的编译产物是**工作流阶段与 tools/ 引擎**，
  不包含门禁；
- 本协议是 RSI 之外的**平行治理轨道**：门禁的演化同样"学习自事故"，但决策权、节奏与
  验证方式独立——两道轨道的交点只有一处：事故教训（LESSONS）既是 RSI 的输入，也是门禁提案的动机来源。
